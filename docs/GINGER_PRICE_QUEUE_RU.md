# Локальная очередь навигации и чтения Ginger

`PriceVisitQueue` хранит план и последовательные квитанции. Никакое состояние очереди не разрешает менять товары: `products_processed=false`, `can_write=false` сохраняются даже в конце списка.

## Режимы плана

- Старые планы и `create()` без `require_read=True` подтверждают только открытие документа. Их политика не меняется при обновлении.
- Новые планы экспериментального Windows-контроллера создаются с `require_read=True`. После открытия остаётся `awaiting_read=true`: следующий переход запрещён, пока не принят снимок выбранной позиции и кандидатов. Это **одна выборочная позиция**, не весь прайс.

`observed_documents` считает подтверждённые открытия. `sampled_documents` считает документы с принятым снимком одной выбранной позиции. Пустая панель кандидатов не доказывает отсутствия товара в каталоге. `SearchCompletionVerified=false` и `IdentityVerified=false` обязательны: стабильные снимки не доказывают завершение поиска или идентичность товаров.

## Контракт

1. `create(report, require_read=...)` сохраняет полный список: номер, поставщик, дата и галочка каждой строки, включая неотмеченные. Одинаковые поставщики не объединяются; порядок не сортируется автоматически.
2. `next(fresh_report)` / `begin(fresh_report)` сверяют весь список с планом. Изменённые поля, порядок или галочки блокируют продолжение. `begin` создаёт исключительную запись намерения **до навигации**.
3. `observe(attempt, document)` сверяет номер и поставщика открытого документа. В режиме обязательного чтения намерение остаётся незавершённым и блокирует следующий документ.
4. `record_read(attempt, snapshot)` сверяет документ, строгие флаги, выбранную строку, названия, порядок и предел кандидатов. Записываются SHA-256 снимка, количество кандидатов и наблюдаемая позиция строки. Полный снимок отдельно остаётся в локальной диагностике. После этого можно выбрать следующий документ.

Снимок принимает только доверенный вызывающий код после собственных проверок UI. JSON-файл, номер строки или хеш сами по себе не являются доказательством подлинности интерфейса или ID товара.

## Сохранность состояния

План — `plan.json`, события — последовательные `000001.json` и далее. Записи создаются исключительно, с flush/fsync, не перезаписываются. Два процесса не могут добавить одно событие одновременно. Пропуски, повреждение, неизвестные файлы и неверные переходы блокируют продолжение. Политика чтения и незавершённая попытка сохраняются при перезапуске. Автоматического сброса, пропуска и повтора ввода при неизвестном исходе нет. Это не абсолютная гарантия сохранности при физическом отказе накопителя.

## Windows-контроллер

`scripts/windows/ginger-queue-step.ps1` требует исходный checkout:

- `Initialize` читает уже видимый список и создаёт новый план с обязательным чтением.
- `Status` читает только локальный журнал.
- `Step -ConfirmNavigation` сверяет список, сохраняет намерение, выделяет и открывает прайс, проверяет номер/поставщика, выбирает «Сопоставление - новые», открывает нижнюю панель при необходимости, читает позицию и кандидатов, затем сохраняет квитанцию чтения.
- `ReadCurrent -ConfirmNavigation` доступен только для уже открытого документа, ожидающего чтения. До навигации по вкладке повторно сверяются номер и поставщик с незавершённой попыткой. Повторного открытия документа нет.

Фиксированный `ginger-queue-cli.py` загружает ядро из того же checkout без строк Python-команд в shell. Диагностический harness `GingerDiagnostics.Smoke --queue-controller` ограничивает процесс 60 секундами и объём вывода, завершает дерево дочерних процессов при тайм-ауте. При прямом вызове PowerShell этого внешнего ограничения нет. `ConfirmNavigation` не заменяет разрешения Agent Runtime; контроллер пока не подключён к его штатным командам. Не запускайте разные планы одновременно против одной сессии Ginger: глобальная блокировка между каталогами ещё не реализована.

## Проверка на устройстве

В новом плане из 48 прайсов подтверждены два открытия и два выборочных чтения. Первая попытка остановилась на распознавании уже активной синей вкладки, сохранив `awaiting_read=true`. Обнаружено, что порог обработки снимка стирал светлые буквы; после коррекции `ReadCurrent` завершился без повторного открытия. Следующий документ прошёл весь шаг одним запуском. Итог: `observed_documents=2`, `sampled_documents=2`, `pending_attempt=null`, `products_processed=false`.

Изменение порога проверено на текущей теме Ginger. Другие темы, DPI и конфигурации мониторов этим испытанием не покрыты. Возврат к списку пока выполняется отдельным вызовом драйвера. Обход каждой товарной строки, устойчивые ID, завершение поиска, автоматический цикл всех 48 прайсов и интеграция разрешений Runtime остаются незавершёнными. Фоновых запусков не добавлялось.

Локальные проверки: 34 теста очереди, включая восстановление ожидающего чтения, неправильный документ, неподтверждённые права, повреждённую квитанцию, пустых кандидатов и совместимость старых планов. Полный Python-набор: 584 passed, 1 skipped. Данные поставщиков, снимки и живые квитанции в GitHub не отправляются.
